# Auth Integration

## Overview

Auth is implemented with py4web `Auth` and a project-specific wrapper in
`py4web/common/models/backend/auth_cls.py`.

Classes:

- `AppAuth(Auth)`: custom auth adapter (`auth_cls.py`).
- `LoggingAuthForms(DefaultAuthForms)`: logs auth actions to applog (`auth_forms.py`).

The web integration delegates shared authorization behavior to:

- `AuthAdapter`: runtime bridge from py4web to shared auth contracts
- `AuthContext`: framework-agnostic actor, membership, and permission API used by modules and policies

See [Auth and RBAC](../architecture/auth-rbac.md).

## Enabled Actions

Configured `allowed_actions`:

- `login`
- `logout`
- `request_magic_login`
- `magic_login`
- `request_reset_password`
- `reset_password`
- `change_password`
- `profile`
- `register`
- `verify_email`

## Mail + Logging Hooks

- Outbound auth mail is attached by `AppAuth.from_dependencies(...)` via `auth.sender = backend.mailer`.
- Auth actions are logged through `Applogger.log_auth_action(...)`.
- Login failures are recorded as `invalid_login_attempt`.
- Magic-login requests send a one-time login link through the same mailer and record
  both the request and token-consumption result.

Logged metadata includes:

- action
- success/failure
- user gid / email (if available)
- request IP
- user agent

## Session and Browser Mutation Limits

Redis-backed sessions use `REDIS_PASSWORD`, generated by `edwh setup`. Deploy the
password to Redis, its replica and application containers together, then recreate
those services. Existing environments must run setup before starting the updated
Compose configuration.

Authenticated sessions expire after seven days without a successful request
(`SESSION_IDLE_SECONDS=604800`) and thirty days from login
(`SESSION_ABSOLUTE_SECONDS=2592000`). Logout and login rotation revoke the previous
ID. Revocation markers prevent concurrent requests from restoring access with an
old ID. Signed grid action URLs expire after seven days
(`SIGNED_URL_SECONDS=604800`).

Custom mutation handlers using the common/admin/supplier fixture chains require
an exact matching `Origin` or `Referer`. Browser forms and fetch/HTMX requests send
these headers; scripted clients must send the application's origin too. Missing
or cross-origin headers receive HTTP 403. Entree callbacks use a fresh,
session-bound OAuth state that is consumed and checked before exchanging a code.
SSO callback success and failure are logged independently of password-form events.

Uploads allow 50 MiB per file (`UPLOAD_MAX_BYTES=52428800`). The request parser also
bounds complete request bodies to that limit plus 1 MiB for form metadata. AI
inputs allow 20,000 characters per free-text field (`LLM_FIELD_MAX_CHARS`) and
100,000 user-input characters per call (`LLM_CALL_MAX_CHARS`). Oversized inputs
are rejected, never silently truncated.

## Membership Refresh

Membership assignment is part of the auth flow:

- `store_user_in_session(...)` refreshes memberships after a successful login.
- `grant_roles_after_email_verification(...)` refreshes memberships after email verification.
- `SupplierBackend` matches the user's email domain against `supplier.email_domains` and grants membership to the matching supplier RBAC identity.
- `OrganisationBackend` matches the user's email domain against `organisation.email_domains` and grants membership to the matching organisation RBAC identity.
- Access checks use `AuthContext` membership plus RBAC inheritance and permissions, not an environment-variable whitelist.

See [Supplier memberships and access control](../architecture/supplier-memberships.md) and [Auth and RBAC](../architecture/auth-rbac.md).

## Password Reset Policy

- Password reset links expire after 72 hours.
- The expiry timestamp is stored on `auth_user.reset_password_expires_at`.
- `request_reset_password` writes the expiry when a reset token is created, and reset-token validation checks it before allowing the reset flow to continue.
